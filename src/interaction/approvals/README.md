# Approvals

An `Approval` owns one immutable request and one irreversible decision. Its capability policy defines the advertised choices, how existing grants match the requested operation, and the effects of a selection. A UI sends an approval ID and a choice ID; it cannot supply authority or a grant.

`ApprovalCoordinator` separates the decision from admission and from the outcome of saving a grant. It never executes the operation. Callers execute only after an authorized result and a final cancellation check. A grant-bearing allow saves before admission. A grant-bearing denial stays denied even if saving fails. Cancellation during a write lets that write settle, reports any saved grant, and suppresses execution. `ApprovalQueue` keeps a cancelled queued caller from advancing an earlier prompt or write.

| Capability   | Current operation                                                         | Remembered authority                                              | Timeout                                                                                 |
| ------------ | ------------------------------------------------------------------------- | ----------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Shell        | Deny; sandboxed allow; read-only inspection; explicitly unsandboxed allow | Exact command and directory; safe inspections; all shell commands | None                                                                                    |
| Internal web | Deny or allow one checked HTTP hop                                        | All internal destinations in this workspace                       | Consent pauses the cumulative network deadline                                          |
| Goal         | Deny or start the proposed goal                                           | None                                                              | None                                                                                    |
| Mode switch  | Deny or apply the proposed change                                         | None                                                              | Starts on display; records the configured timeout decision separately from user consent |

Shell's “Allow & enable safe commands” allows the current command in the appropriate sandbox and remembers future read-only inspections. “Deny & enable safe commands” denies the current command and saves the same preference. Background processes and existing terminals never qualify as automatic safe inspections. Desktop advertises only sandboxed choices; terminal also advertises explicit unsandboxed choices.

Grants bind both workspace identity and mutation scope. Shell and web grants cannot authorize each other. Shell matching preserves the existing precedence: all-shell authority, then an exact command/directory grant, then safe inspection authority. Each admission reloads the grant repository; UI state is not authority.

`ApprovalGrantSet` owns the immutable collection of remembered permissions: scope filtering, policy-based selection, and replacement of equivalent grants. Hydration through `from()` keeps the last equivalent record, including its decision provenance; `withGrant()` returns a new set and preserves unrelated scopes and permissions. Capability policies still define matching and precedence. `toRecords()` produces detached plain records for persistence. Repository revisions stay outside the set, so preparing a replacement cannot advance the persisted revision or bypass the coordinator's save-before-admission rule.

`FileApprovalStore` reads bounded, uniquely linked regular files without following final-component symlinks. It writes private snapshots with exclusive temporary files and atomic replacement. An exclusive update lock plus an opaque content revision prevents silent lost updates. A concurrent or abandoned lock fails closed; the store does not guess whether it may remove another writer's lock. A revision conflict requires a fresh decision. Parent-directory ownership remains an operating-system trust assumption; this is not protection against another process running as the same user.

The first successful save imports compatible `shell-permissions.json` and `internal-web-approvals.json` grants into `approval-grants.json`. Legacy shell commands without a directory are not imported. Original files remain intact, and the new snapshot becomes authoritative. `LegacyShellApprovalStore` supports callers of the previous shell-only store port; production factories use the generic repository.

Security tests contain their own threat descriptions and expected boundaries. They cover domain transitions, UI choices, cancellation, expiry, persistence failures, migration, scope isolation, and transport admission. These tests do not establish native sandbox enforcement; that has separate disposable-fixture tests.
