# Shell sandbox adversarial threat model

Reviewed **2026-10-07**, against commit `a82016548f39b7c2092d8775f753420c46d5d0c9` and its initially clean working tree.

This is a static review of Glyph's shell authorization, native sandbox, and surrounding trust boundaries. It inventories plausible attack families and relevant public vulnerabilities; it does not claim that every possible escape can be enumerated. No exploit, adversarial probe, sandbox command, build, or test was executed. Existing tests were read as source. Public vendor and maintainer advisories were consulted for the CVE register. Installed OS and backend versions were not inspected, so this is not a finding that this Mac, or any particular Linux installation, is vulnerable to a listed CVE.

The most actionable concerns are in policy construction and trust transitions: Linux resolves its sandbox backend through `PATH`; repository-controlled Git metadata becomes additional Linux filesystem mounts; macOS turns `PATH` directories into recursive read permissions; and secret-file exclusions are incomplete snapshots. Interactive input, cross-chat terminal access, self-hosted development, writable trace destinations, and elevated trust in shell wake output add ways to cross an application boundary without breaking the kernel sandbox.

All attack descriptions below are conceptual. The [adversarial-testing safety policy](test/ADVERSARIAL_TESTING_SAFETY.md) governs any separately authorized future evaluation. Listing an avenue here does not authorize testing it, and the policy prohibits several listed classes from execution altogether.

## 1. Security model and evidence vocabulary

Assume an adversary can influence model tool requests, repository contents, dependency scripts, build output, and files writable by an approved shell command. Treat the running command as arbitrary hostile code, including code launched indirectly by a seemingly ordinary tool. Separately consider a compromised host environment or package-manager installation: those are stronger prerequisites, and findings identify them where needed.

Assets include host files and credentials; Glyph accounts, approvals, traces, and chat state; repository metadata; other workspaces and chats; host processes and IPC services; network access; and availability of the workstation. The trusted computing base includes Glyph's unsandboxed Node process, its loaded and subsequently loaded code, native helper and dependencies, sandbox backend, host kernel, and any reachable host service acting on the command's behalf.

The following labels distinguish evidence from inference:

- **Observed:** the cited code implements this permission, omission, or data flow. It is not an experimentally confirmed escape.
- **Conditional:** the consequence follows only when a stated deployment or attacker-control prerequisite holds.
- **Hypothesis:** a plausible OS or integration avenue whose reachability and effect remain unverified.
- **Mitigated:** a relevant avenue for which a specific control is visible; this is not proof against every variant.
- **By design:** explicitly granted authority or an inherent channel, rather than a sandbox bypass.

Risk priorities below are qualitative review priorities, not CVSS scores. A successful escape could be a forbidden read, write, host-side execution, or unauthorized use of an already privileged session. Denial of service and leakage through allowed output are also threats, even where they are not escapes.

## 2. Findings to address first

### F1 — Linux executes a `PATH`-selected backend before confinement

**High; observed trust gap, conditional host execution.** The native helper calls `Command::new("bwrap")`. For workspace-write commands, the TypeScript launcher preserves the host's ordinary `PATH`. If an earlier search directory contains an attacker-controlled replacement, the helper can execute that replacement before a genuine sandbox exists. A relative or workspace-local search directory makes this particularly relevant to repository-controlled content. Even the read-only path trusts package-manager binary directories; their names alone do not establish ownership or immutability.

This does not require an OS sandbox vulnerability. It requires control of a location the unsandboxed helper searches. The native helper itself and environment overrides also remain bootstrap trust dependencies.

**Hardening direction:** select the backend by a validated absolute path; establish ownership, permissions, provenance, and supported patch level outside attacker-writable roots; reject overlap between trusted launch inputs and writable projects. Preserve failure on missing or invalid backends.

Evidence: [lib.rs](../../native/shell-sandbox/src/lib.rs), lines 361–375; [NativeShellSandboxLauncher.ts](NativeShellSandboxLauncher.ts), lines 125–150; [cli.ts](../cli.ts), lines 73–112.

### F2 — Untrusted Git metadata can expand Linux host read mounts

**High; observed policy-construction gap, unexecuted consequence.** `repository_metadata_paths` reads a `.git` file, accepts its `gitdir:` target, and canonicalizes any existing target without constraining it to a trusted repository metadata location. The Linux builder then adds a read-only bind mount for every returned path. Repository content therefore participates in granting access to host paths that were absent from the initial mount allowlist.

The later home-secret masking checks whether a secret is inside a workspace root, not whether an extra metadata mount exposed it. The state-directory overlay protects its declared path, but does not make arbitrary added mounts safe. On macOS, the same discovered paths become write denials, so this particular read-grant consequence is Linux-specific.

**Hardening direction:** discover and validate Git administrative paths through a trusted repository model. Do not turn repository-supplied paths into new read authority merely to protect them from writes; protect only necessary metadata with explicit bounds and account for every mount in confidentiality checks.

Evidence: [lib.rs](../../native/shell-sandbox/src/lib.rs), lines 235–263, 458–465, and 603–632.

### F3 — macOS `PATH` entries become broad read permissions

**High confidentiality concern; observed, conditional on inherited path configuration.** The macOS policy grants recursive reads to each `PATH` entry. It excludes literal `/` and the exact home path before canonicalization, then canonicalizes the entry or retains the unresolved spelling. Aliases, ancestor directories, and alternate spellings can consequently produce grants broader than intended. Explicit state and known-secret denials still apply at their matched paths; other personal data has no general exclusion.

The implementation also intentionally exposes broad system and toolchain trees. Read access can therefore extend beyond project content even without the alias issue. Any readable information can enter ordinary tool output and subsequently provider requests.

**Hardening direction:** separate executable search from data-read authority; canonicalize before validation; reject broad ancestors and untrusted aliases; use a small explicit runtime/toolchain read set rather than deriving recursive access from arbitrary `PATH` entries.

Evidence: [lib.rs](../../native/shell-sandbox/src/lib.rs), lines 421–442 and 482–515; [NativeShellSandboxLauncher.ts](NativeShellSandboxLauncher.ts), lines 125–145.

### F4 — Secret-file protection is a partial, name-based startup snapshot

**High confidentiality concern; observed coverage gaps.** The workspace scanner ignores symlinks and does not descend into `.git`, `.next`, `coverage`, `dist`, or `node_modules`. It records only existing regular files with a short, case-sensitive set of names or suffixes, and explicitly exempts `.env.example`. Secrets in generated output, caches, ignored directories, differently named files, Git objects, or files added after launch are not covered by that scan. A name convention cannot determine whether content is actually confidential.

Linux hides recorded files by mounting `/dev/null` over their paths; macOS denies recorded literal paths. Neither mechanism establishes that alternate names for the same data, hard links, pre-opened descriptors, or concurrent tree changes are covered. Those variants require separate analysis rather than assuming path canonicalization solves them.

**Hardening direction:** define the intended confidentiality boundary explicitly. Prefer mounting or allowing only needed content, and treat sensitive-name filtering as defense in depth. Apply consistent exclusions to every exposed tree and to changing content; do not promise that all credentials are hidden based on this scanner.

Evidence: [lib.rs](../../native/shell-sandbox/src/lib.rs), lines 266–325, 437–442, 611–632, and 651–698.

### F5 — Linux home-secret masking misses roots inside a sensitive directory

**High; observed containment-direction gap.** A home-sensitive path is masked only when `path.starts_with(root)`. A workspace root that lies beneath a sensitive directory reverses that relationship, so the directory's protection is skipped. The broad-root validator rejects the home directory and certain exact system paths, but does not generally reject descendants of sensitive directories. Alias handling and added Git mounts complicate this further.

This requires a dangerous workspace configuration or manipulation of root selection; a command cannot simply supply a new root through the shell tool schema. macOS has a different mechanism, with explicit sensitive-directory subpath denials, so the implementations should not be treated as equivalent.

**Hardening direction:** reject overlap in either direction between workspace roots and sensitive/trusted locations after canonicalization, and include non-workspace exposure such as additional mounts in the same policy model.

Evidence: [lib.rs](../../native/shell-sandbox/src/lib.rs), lines 162–213 and 619–632; [ShellToolRuntime.ts](ShellToolRuntime.ts), lines 9–28.

### F6 — Self-hosted source remains writable before later trusted execution

**High conditional integrity concern; delayed host execution, not a demonstrated immediate escape.** CLI wiring protects two native executable paths. When Glyph's own checkout is a writable workspace, its source, package scripts, dependency content, Rust build inputs, and launch configuration are not collectively protected. The normal `pnpm start` path builds native code and runs TypeScript outside the command sandbox. A prior sandboxed modification can therefore cross the boundary when trusted host tooling later consumes it.

The same class includes workspace files consumed by unsandboxed IDE plugins, file watchers, task runners, preview services, or subsequent outside-sandbox commands. The sandbox may correctly allow the initial workspace write while the larger workflow still permits host-side consequences.

**Hardening direction:** run the trusted application from an installation outside writable projects; protect its dependency and launch chain; make execution of workspace-derived content a deliberate trust transition. Protecting the current executable inode or path alone is insufficient.

Evidence: [cli.ts](../cli.ts), lines 73–112; [package.json](../../package.json), `start`, `context-index:build`, and `shell-sandbox:build`; [lib.rs](../../native/shell-sandbox/src/lib.rs), lines 332–337, 448–472, and 594–609.

### F7 — Running terminals carry authority beyond a command-string approval

**High when full-access processes are involved; observed application boundary gaps.** `write_shell_input` forwards bytes to a running child without a fresh authorization decision. An interpreter, REPL, or interactive tool can interpret those bytes as further commands. A one-time full-access approval consequently grants the running process authority for its lifetime, including later model-written input. The tool description's statement that raw input cannot start a new command does not hold for command interpreters.

Additionally, `ownerChatId` is metadata, not access control: terminal listing returns all background terminals, and lookup checks only whether an ID exists. With the shared session manager, another chat can discover and interact with an earlier chat's terminal, including a privileged one. Reusing an idle terminal through `execute_shell` does request authorization again; that control does not cover input to an already running child.

**Hardening direction:** bind read/write/close operations to an authenticated chat or actor; persist the process's granted authority in session state; explicitly authorize interactive sessions at that authority and constrain transfer between chats. If per-command approval is intended, arbitrary interpreter stdin cannot bypass it.

Evidence: [ShellSessionManager.ts](ShellSessionManager.ts), lines 50–58, 77–103, 130–141, 185–188, and 254–315; [ShellToolRuntime.ts](ShellToolRuntime.ts), lines 49–54 and 101–129.

### F8 — A workspace trace destination can expose a trusted host writer

**High, configuration-dependent; observed path-following, hypothetical redirection.** `CHAT_TRACE_FILE` may select a destination inside a workspace. Project read/edit tools exclude that path, but the shell launcher's protected paths omit it. Unless another rule happens to cover the location, a sandboxed command can read or change the workspace trace. Subsequent unsandboxed logging uses pathname-based `appendFile` and `chmod` without a no-follow mechanism.

If the trace pathname or its ancestry is replaceable, the logger can act as a deputy that follows an attacker-controlled alias on a later write. The exact redirection sequence was not attempted. The default trace lives under the protected state directory; this finding requires a custom exposed destination and subsequent logging. Trace disclosure also matters because tool output and provider state can contain sensitive project information.

**Hardening direction:** require trace storage outside writable roots with trusted ancestry, apply protections consistently across tools, and retain a safely opened destination whose identity cannot be replaced between appends. A write-only exclusion would not solve trace confidentiality.

Evidence: [EnvironmentConfigurationProvider.ts](../configuration/EnvironmentConfigurationProvider.ts), lines 101–102; [cli.ts](../cli.ts), lines 65–68, 108–113, and 217–225; [FileLogger.ts](../observability/FileLogger.ts), lines 32–41; [AgentRuntime.ts](../chat/runtime/AgentRuntime.ts), lines 145–152.

### F9 — Shell wake output is promoted into a developer-role message

**High application trust concern; observed data flow, untested injection success.** Wake matching copies command-controlled output after stripping terminal control sequences. The terminal application stores that output inside a `shell_wake` context event and automatically sends another agent turn. The OpenAI adapter serializes the entire event as a developer-role message. Untrusted process output therefore enters a channel normally reserved for application instructions.

JSON encoding and VT stripping do not establish semantic trust in the text. Malicious output could try to influence subsequent tool use, exploit existing persistent approvals, or induce an outside-sandbox permission request. Existing authorization and sandbox checks still apply to resulting tool calls; this observation does not prove that the model follows injected instructions or that the OS boundary is bypassed.

**Hardening direction:** keep trusted wake metadata separate from untrusted command output, retain output at tool/data trust, and ensure automatically resumed turns cannot expand authority merely because an event occurred.

Evidence: [ShellSessionManager.ts](ShellSessionManager.ts), lines 335–348; [TerminalApplication.ts](../terminal/TerminalApplication.ts), lines 259–278; [OpenAIProvider.ts](../providers/openai/OpenAIProvider.ts), lines 299–303.

### F10 — Allowed IPC needs its own authority review

**High potential impact; observed access, hypothetical broker abuse.** macOS permits six Mach service names and unrestricted `ipc-posix-shm` in the generated profile. Direct file or network denial does not by itself establish what those services may do for a caller, or what existing shared-memory objects are reachable. Service authorization, inherited Mach rights, extension tokens, and OS patch state matter.

Linux exposes workspace objects through bind mounts. A pathname Unix socket or FIFO inside an exposed tree is an IPC endpoint, not ordinary passive file content. Network namespaces alone do not establish safety of filesystem-visible host brokers. Actual access still depends on socket permissions, backend behavior, and the service's authorization.

**Hardening direction:** justify each broker and IPC capability, minimize exposed endpoints, and require the host service to authenticate and constrain requests. Review these surfaces statically; no host-service or other-process probing is authorized here.

Evidence: [lib.rs](../../native/shell-sandbox/src/lib.rs), lines 405–416 and 588–601. Bubblewrap's own [security limitations](https://github.com/containers/bubblewrap/blob/main/README.md) identify exposed IPC services as a potential route to host execution.

## 5. Threat classes and weakness taxonomy

The inventory spans spoofing (approval and executable identity), tampering (workspace and trusted-consumer inputs), repudiation (approval/session attribution), information disclosure (broad reads, aliases, output, IPC), denial of service (unbounded work and missing quotas), and elevation of authority (pre-sandbox execution, host brokers, and kernel flaws).

Useful weakness families for tracking issues are:

- **Path traversal and link resolution:** CWE-22 and CWE-59; root confinement, aliases, mounts, and repository-supplied paths.
- **Check/use races:** CWE-367; canonicalization, traversal, mounts, executable identity, and approvals against mutable content.
- **Executable search paths:** CWE-426/CWE-427; the boundary between trusted launchers and writable search directories.
- **Argument injection:** CWE-88; hostile data becoming backend configuration rather than child arguments.
- **Missing or incorrect authorization:** CWE-862/CWE-863; session ownership, interactive authority, root scope, and policy reuse.
- **Confused deputies:** CWE-441; host services, watchers, portals, and other consumers exercising greater authority on attacker-controlled input.
- **Information exposure:** CWE-200; sensitive data readable through gaps or returned through ordinary output.
- **Uncontrolled resource consumption:** CWE-400; process, memory, storage, scanning, and output limits.

These are descriptive mappings, not formal CWE assignments for independently confirmed vulnerabilities. Ordinary arbitrary shell execution is the tool's purpose; it should not be mislabeled as an injection vulnerability merely because it accepts shell syntax.

## 6. Existing assurance and remaining gaps

Visible defenses include strict tool schemas, canonical working-directory confinement, state/root non-overlap checks, no automatic unsandboxed fallback, explicit outside-sandbox choices, a reduced sandbox environment, startup-file suppression, command/backend argv separation, default-deny Seatbelt policy, namespace isolation on Linux, state concealment, protected executable paths, output retention limits, and post-approval lifecycle checks.

The existing native test source describes fixture-only checks for an ordinary read/write, read-only write denial, direct outside writes, symlink traversal, existing root/nested Git metadata, state access, a synthetic home credential, temporary writes, and one loopback TCP case. **It was not run during this review.** The test is marked ignored; the normal `shell-sandbox:test` script does not enable ignored tests, and the checked-in CI has an Ubuntu job only. Existing unit tests inspect generated policies or mock process launch; that is useful but not equivalent to host enforcement coverage.

There is also a static cross-platform test mismatch: the project-secret test requires `cat` to fail, whereas Linux hides that file with a readable `/dev/null` bind mount. Empty successful output can satisfy confidentiality while violating the test's exit-status assertion. This could make a future Linux run report an “escape” for successful masking. The claim here is about source semantics, not an observed test failure.

Evidence: [native test](../../native/shell-sandbox/tests/sandbox_e2e.rs), lines 14–102 and 255–259; [Linux masking](../../native/shell-sandbox/src/lib.rs), lines 611–613; [package scripts](../../package.json); [CI workflow](../../.github/workflows/ci.yml).

Unresolved assurance questions include effective backend/version selection; actual minimum supported macOS and Linux configurations; Git-worktree/alias handling; descriptor inheritance; allowed Mach-service authority; filesystem socket exposure; concurrent tree changes; process-tree termination; and whether confidentiality, chat isolation, and self-hosting are intended guarantees. None should be represented as experimentally verified by this document.

## 7. Recommended order of follow-up

1. **Remove pre-confinement authority from untrusted inputs.** Resolve and validate Linux's backend explicitly, stop untrusted Git pointers from expanding mounts, and separate the trusted Glyph installation from writable projects.
2. **Make the filesystem policy explicit and consistent.** Remove automatic broad `PATH` read grants, reject sensitive/trusted root overlap in both directions, and define how secrets, aliases, new files, Git metadata, and all extra mounts are handled.
3. **Keep application trust separate from command output.** Move traces out of writable roots, protect their open-file identity, and keep wake output out of developer-role instructions.
4. **Treat sessions as capabilities with owners.** Enforce chat/actor ownership, record sandbox authority, and make interactive process lifetime and root scope part of approval semantics. Reconsider saved permission when workspace membership changes.
5. **Reduce host interaction and shared-kernel exposure.** Review each Mach/IPC permission and Linux exposed endpoint; consider syscall restrictions and resource limits where they match the support contract. A VM boundary is an architectural option if the intended guarantee includes containment of hostile native code despite host-kernel flaws.
6. **Establish patch and assurance requirements.** Track vendor fixes and distribution backports for the actual deployed OS/backend; maintain macOS/Linux-specific enforcement evidence; fix test expectations that confuse successful masking with denial failures.

These are review recommendations only. This change implements no hardening and grants no permission for exploit execution. Any subsequent evaluation must obey the linked safety policy, including its prohibition on destructive, denial-of-service, privilege-escalation, real-secret, persistence, other-process, and external-network testing.
